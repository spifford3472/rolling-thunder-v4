## Roll back Checkpoint 0

If the corrected base unit fails physical acceptance:

1. stop the dashboard service;
2. restore the repository checkout to `v4.2.0`;
3. restore/install the v4.2.0 base unit if it was replaced;
4. if required by the restored v4.2.0 base unit, restore the archived
   `v4.2-main.conf.retired-cp0` as
   `/etc/systemd/system/rolling-thunder.service.d/v4.2-main.conf`;
5. run `systemctl daemon-reload`;
6. start `rolling-thunder.service`;
7. verify the dashboard launches from
   `/home/geoff/projects/rolling-thunder-v4` using the production `.venv`;
8. verify radio, GPS, controls, map, logging, and other v4.2.0 functions.

## Checkpoint 2 FT8 domain/application foundation

Checkpoint 2 adds only repository-level Python domain/application code, typed
configuration, tests, and documentation.

The configuration shape is:

```yaml
ft8:
  enabled: false
  qso:
    attempts_per_state: 6
```

Existing configurations without an `ft8` section remain compatible and receive
these disabled defaults.

Checkpoint 2 does **not** change or install:

- production systemd units or drop-ins;
- udev rules;
- PipeWire or ALSA configuration;
- Linux groups or permissions;
- serial-device configuration;
- Python or native dependencies;
- SQLite schemas or contact data;
- FT-891 CAT/PTT behavior;
- DigiRig audio capture or playback;
- decoder software;
- waveform generation or RF transmission.

The FT8 domain is intentionally not composed into `ApplicationRuntime` yet.
Therefore `ft8.enabled: false` creates no FT8 worker or hardware resource, and
even `ft8.enabled: true` at Checkpoint 2 only parses configuration; it does not
start FT8 runtime behavior.

Rollback is repository-only: revert the Checkpoint 2 merge/commit or restore the
protected `v4.2.0` tag. No host-resource reversal or database recovery is
required.

### Planned Checkpoint 3 native build dependencies on anvilmobile

These packages are required only for the isolated decoder bake-off and are not
used by the production Rolling Thunder service:

- `libfftw3-dev` — required by `ft8mon` FFT code.
- `libsndfile1-dev` — required by the stock `ft8mon` WAV-file build.
- `portaudio19-dev` — required by the stock `ft8mon` link step even though
  Checkpoint 3 will not open a live audio device.

Install location: normal Debian system package locations managed by APT.

Production use: none. `rolling-thunder.service` remains pointed at the
production checkout and does not compose either decoder.

Planned installation command:

```bash
sudo apt-get update
sudo apt-get install -y libfftw3-dev libsndfile1-dev portaudio19-dev
```

Rollback/removal after the experiment, if these packages were not present
before Checkpoint 3:

```bash
sudo apt-get remove --purge -y libfftw3-dev libsndfile1-dev portaudio19-dev
sudo apt-get autoremove -y
```

Before removal, compare against the recorded preflight package state so no
pre-existing package is removed accidentally.

`kgoba/ft8_lib` itself requires no system install for the saved-WAV demo
build; it will be built inside the experimental worktree/tool directory.

WSJT-X is not yet authorized for system-package installation. Prefer an
isolated official ARM64 build/reference invocation if practical. If a system
package becomes necessary, document its exact version, install command, and
rollback here before installation.
