# Issue353: response-body deduplication and missing predictions

The scheduled-capture response table is a content-addressed store keyed by canonical response JSON SHA256. Its service_version/model_version columns retain the FIRST stored observation and must not be rewritten when identical bytes arrive from a later provider version. Each capture request separately records the provider/model identity verified for that specific POST. The blob's first-observation metadata is not the authority for a later request's issuer. Compare canonical bytes on a duplicate hash; retain hard failure on different bytes. Existing plan/result identity checks still reject an incoming ProviderResult that does not match its current plan. No schema migration, historical rewrite or forecast reuse is introduced. Every scheduled request still calls the provider.

The previous implementation compared the first blob's version fields against every new result and rejected identical response bodies across provider upgrades. A deterministic two-version105-request regression fails before correction and passes after, while every previously stored response row remains unchanged. This matches the observed30ready/75failed pattern after the rounding correction changed17m/12m bodies but left other bands' bodies stable; exact attribution of protected production failure reasons remains unverified until saved aggregates are read.

Missing prediction fields are never zero or a ranking sentinel. The provider analysis correction (separate voacap-service0.3.2 candidate, versioned in the infrastructure repository) validates required frequency, reliability and SNR and omits incomplete/nonfinite/invalid candidates before peak/hour selection. A valid0reliability and negative finite SNR remain valid measurements. Diagnostic skipped_predictions records contain only hour/band/reason, not fabricated prediction values. Invalid hours are omitted. If all candidates are missing, prediction/summary/recommendation lists are empty rather than an exception.

The capture consumer continues its existing missing-value policy: if either reliability or SNR is absent/invalid for a requested hour/band, BOTH prediction columns are NULL with an explicit unavailable reason. Other complete hour/band transactions and all other scheduled site/band POSTs continue. Raw immutable response evidence is retained for auditing but is not a usable derived prediction. Successful capture is not proof of an actual QSO outcome.

Tests prove old/new provider-version provenance, historical response non-mutation, continued105calls, corruption rejection, and NULL-pair missingness with419other valid cells preserved. Provider candidate tests reproduce the None/float comparison failure and cover missing/invalid/zero/negative metrics, mixed candidates, empty output and invalid hours. No live provider diagnostic requests, history replay, Pi restart, RF/CAT/PTT or new provider enabling is required. This document describes source behavior; exact release, coordinated provider/plan cutover and live-cycle acceptance must be recorded separately in infrastructure documentation.
